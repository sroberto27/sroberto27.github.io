CompleteYour Supabase account

Your database, with its security rules

What it holds Accounts and sign-ins, which company each person belongs to, and who is allowed to see which private tour, map or download.

Checked All eight data tables exist, every one has its access rules switched on, and three specific security fixes were confirmed genuinely active rather than merely listed as installed.

Technical detail

  • Platform. Supabase (managed PostgreSQL 17) in region us-west-1, inside your own organization. Schema applied by running the project’s eight versioned migration files with the Supabase CLI (supabase db push) — the same files, unmodified, that run on the development database.
  • Tables (8). profiles, organizations, organization_members, organization_email_domains, resource_entitlements, client_apps, events, admin_audit.
  • Row Level Security is enabled on all eight, each with its own policies. RLS is enforced by PostgreSQL itself, so access rules cannot be bypassed by a bug in the website code.
  • Verified by direct SQL query, not by trusting the tool’s exit code: relrowsecurity true on all eight tables, and all eight migration versions present in supabase_migrations.schema_migrations.
  • The three security fixes, each confirmed in effect: the events table has only a SELECT policy, so anonymous visitors cannot write to it; the columns r2_object_key and access on client_apps are not readable by the anon or authenticated roles, so private download locations stay hidden; and the helper functions is_org_member() / is_org_admin() check the organization’s status as well as the membership’s, so disabling a company actually revokes its people.
  • No development data was copied. The migration run reported seeds: [], and the organization, membership, app and entitlement tables all return a count of zero.

Website hosting

What it is The service that serves the site to visitors worldwide, plus the small programs behind sign-in, private content and the contact form.

Cost Free at your expected traffic, and it stays free on this plan.

Technical detail

  • Cloudflare Pages project named dts-website, created in Direct Upload mode with no Git connection — deploys are pushed deliberately rather than triggered by a code commit, so nothing reaches your account without an explicit action.
  • Pages Functions provide the server-side behaviour: sign-in checks, serving private content, and access-gated downloads. These run at Cloudflare’s edge; there is no server to patch or maintain.
  • Three secrets are configured on the project’s production environment — the Supabase URL, the public key and the service key. All were generated fresh on your side; none were copied from the development environment. They are stored encrypted by Cloudflare and are not readable back, not even by us.
  • Storage bindings connect the Functions to your two file-storage buckets by name, resolved at deploy time rather than hardcoded.

CompleteYour Cloudflare account

Two file-storage areas

What they hold One for website content — text, project pages, maps. One for downloadable applications you make available to specific clients.

Technical detail

  • Cloudflare R2 buckets named dts-content and dts-builds. The names are fixed — they are referenced by the site’s configuration and by three of its maintenance scripts.
  • Neither bucket is public. R2 buckets are private by default, and these were never given a public address. Everything is served through the Pages Functions, which is what allows access checks to happen before a file is handed over.
  • Placement. Cloudflare placed both buckets in its Eastern Europe region. A relocation to North America was attempted while they were still empty; Cloudflare accepted the request but kept its own placement, which appears to be determined by the account rather than selectable. The practical effect is small and was measured rather than assumed: content responses are cached at the edge for five minutes, so only the first request per edge location per five minutes involves the bucket at all.
  • Downloads bucket is currently empty. Applications are uploaded through the site’s own admin screen, not by this setup process.

CompleteYour Cloudflare account

All website content uploaded

Checked Every page the site asks for loads correctly, and the public copy of each project genuinely has its private tour and map links stripped out — verified on the stored files themselves, not just in the code that writes them.

Technical detail

  • Content is split into two sets before upload. A public set (26 files) contains only what any visitor may see. A private master set (59 files) holds the complete originals, including the private tour addresses and map identifiers. Only the public set is ever reachable from the web.
  • How the split is proved. One example project carries both a private tour address and a map identifier in the master copy, and neither in the public copy. This was checked by downloading both files back out of your storage and comparing them — not by reading the code that produces them.
  • A content index lists every public document. Every entry in it was requested over the live site and all returned successfully. This matters: a single index entry pointing at a file that does not exist previously took an entire site to a fallback state, for all visitors.
  • Two supporting files were also written: a checksum ledger used to work out what changed on the next publish, and a combined bundle of the full document set (52 documents and 6 map data layers) that the admin screen reads so an administrator can edit private content as well as public.
  • Integrity check. Nine files spanning both sets — map data, project documents, site settings and both indexes — were downloaded back and confirmed byte-for-byte identical to the local originals.
06
CompleteYour Cloudflare account

The site deployed, and its protections tested

Checked Internal files are not reachable from the web. A visitor who is not signed in, asking for a private map, is correctly refused rather than shown an error. Security headers are present on every response. Nothing sensitive was published.

Worth being straight about: these checks were run against the live address by machine. A full human click-through of every page, on desktop and phone, has not been done yet — see the last section.

Technical detail — what was tested, and how

  • What was published. 116 static files plus the Functions bundle. Only the site itself was uploaded: the content master files, maintenance scripts, database migrations, internal documentation, tests and developer notes were all excluded by building the upload from an explicit list of what belongs, rather than copying everything and deleting.
  • Proving exclusion is harder than it looks. Cloudflare Pages answers a missing address with the site’s own home page rather than a “not found” error, so a success code proves nothing. Instead, the home page’s exact size was measured (64,898 bytes) and twelve internal paths were each requested and confirmed to return exactly that size — proof they are hitting the fallback and no real file exists there.
  • Access control. An anonymous request for a private map returns 401 “sign-in required”. The distinction between 401 and a 500 error matters: a 500 would mean the check crashed rather than refused, which can fail open.
  • Security headers — x-content-type-options, referrer-policy, content-security-policy and strict-transport-security — confirmed present on server responses, using a full request rather than a headers-only one. A headers-only request falls through to the static page and returns different headers, which can look exactly like the protection being absent.
  • Configuration leak check. The deployed fallback configuration file contains one public tour address, not the sixteen in the internal copy. Confirmed on the live site.
  • Anti-spam widget. The contact form’s check now uses a widget created in your own Cloudflare account. This was found broken during testing — the widget is locked to specific web addresses and had not been re-issued for the new one — then fixed, redeployed and confirmed working in a browser.

Still to come before the site goes public

Roughly in the order they need to happen. The first four are the ones that actually gate a public launch.

07
Blocks launchThird partyStart this first

Control of digitaltwinstudios.com — currently held by the previous developer

Why The site answers on a temporary preview address. Pointing the real domain at it is a launch-day step, and item 09 cannot even begin until the DNS records are reachable.

The actual blocker The domain and the existing WordPress site are still under the control of the previous developer. This is not a decision you can simply make — it depends on a third party responding, which is why it should be started before anything else on this list.

Treat this as the critical path. Everything else here is work that can be scheduled; this one waits on somebody outside the project. Two risks worth naming early: if nobody is clearly responsible for the renewal, the domain can lapse and be bought by someone else, which is effectively unrecoverable; and if company email runs on this domain, a careless change breaks mail before anyone notices the website.

What to request from the previous developer

  1. Registrar account access — where the domain is actually registered (GoDaddy, Namecheap, Google Domains and so on), and login or administrative access to it. Preferably the domain is transferred into an account you own outright, rather than access being shared.
  2. If transferring: ask them to unlock the domain and supply the authorisation code (also called an EPP or transfer code). Transfers typically take 5–7 days and cannot be rushed, which is the main reason to start now.
  3. A full export of the current DNS zone — every record as it stands today. This is the single most important item. Recreating it from memory is how mail and third-party services get broken during a move.
  4. Confirmation of the email setup. Specifically whether MX records point at Google Workspace, Microsoft 365, or the web host’s own mail — plus any SPF, DKIM and DMARC records. These must be carried across before any nameserver change, or email stops.
  5. Renewal and expiry details — the expiry date, who currently pays, and whether auto-renew is on.
  6. What happens to the existing WordPress site — whether it stays reachable during the transition, who hosts it, and when it can be retired. Nothing needs to be switched off until you choose to.

Meanwhile Nothing above blocks the rest of this list except item 09. The preview address keeps working, and continues to after the domain is live.

Once the domain is in your hands

  1. Add it to the Pages project under Custom domains. Cloudflare issues the HTTPS certificate automatically once DNS resolves.
  2. Point the DNS record at the Pages project — a CNAME for a subdomain such as www, or Cloudflare’s flattened CNAME at the root. Moving the domain into Cloudflare’s own DNS handles this for you and makes the rest simpler.
  3. Recreate every non-web record first — mail and any third-party verification records — and confirm mail still flows before switching the web records over. Keep the WordPress site reachable until that is confirmed.
  4. Then re-point two site settings and redeploy: the Supabase connection hint, and the anti-spam widget’s allowed-address list. Neither breaks loudly if forgotten — the first costs a wasted network round trip, the second shows a red box on the contact form, exactly as happened on the preview.
  5. Finally, item 09 becomes possible — the email provider’s verification records need this same DNS access.

09
Blocks launchWaiting on the domain

Custom email sending (SMTP provider + verified sending domain)

Why Invitations, sign-up confirmations and password resets all send email. The built-in allowance is capped at two messages an hour across the whole site, which is unusable for real people.

This is not optional the way social sign-in is. The cap is two messages per hour, project-wide, shared across every type of authentication email — Supabase’s own documentation calls it unsuitable for production. Password reset will appear to work and simply never arrive. It has to be in place before inviting your real users (item 08), and it needs DNS access first — so it inherits item 07’s wait on the previous developer. In practice that makes the chain 07 → 09 → 08, and the whole chain starts with a third party responding.

How to get it

  1. Pick a provider. Resend is the worked example in Supabase’s own documentation; Amazon SES, Postmark, SendGrid, ZeptoMail and Brevo all work the same way. A free tier is sufficient.
  2. Create the account — yours, or managed by Digital Twin Studios on your behalf. This is the same ownership question as the contact form in item 11; decide it rather than defaulting.
  3. Add the sending domain in the provider, and copy the SPF and DKIM records it gives you.
  4. Add those records at the DNS host from item 07 — which requires the domain access being requested there — then wait until the provider shows the domain as verified. Nothing sends until it does; this is exactly the step that was blocked throughout development.
  5. Generate an API key in the provider.
  6. In Supabase: Authentication → Emails → SMTP Settings → enable custom SMTP. For Resend that is host smtp.resend.com, port 587, username literally resend, password = the API key. Set the sender address at the verified domain (for example no-reply@yourdomain.com) and the sender name to Digital Twin Studios.
  7. Then raise the rate limit by hand. Authentication → Rate Limits → “Rate limit for sending emails”. Supabase applies a new default of 30/hour once custom SMTP is active, but the field may still display the old value of 2. Do not assume it updated.
  8. Test both flows for real — a signup confirmation and a password reset. They are two separate code paths sharing one budget.

Where it lives The provider API key goes into the Supabase dashboard, not into any project file.

A decision

Who receives contact-form enquiries

Decision Whether enquiries keep arriving through the Digital Twin Studios account, or move onto an account of your own. Either works; it should be chosen rather than defaulted into. Until then, enquiries sent from the preview arrive with us.

Technical detail

  • How it works. The form posts directly from the visitor’s browser to Web3Forms, using a public access key. Web3Forms documents this key as safe for browser use; their own abuse protection and rate limiting sit on their side.
  • To move it: create a Web3Forms account under your own address, generate an access key, and it replaces the current one in the site’s content settings — editable through the admin screen, no code change.
  • Fallback. If the key is ever missing, the form degrades to opening the visitor’s own mail application with the answers pre-filled, rather than failing silently.
  • Anti-spam. A Cloudflare Turnstile widget, now on your account, gates the submit button in the browser. It is a deterrent rather than a strict gate: if the widget cannot load, the form deliberately still allows submission rather than trapping a legitimate visitor. There is no server-side token verification in the current design — a simplification made deliberately during development, and worth knowing rather than discovering.

    An invitation to a third address on your Supabase account is showing as expired. It grants nothing while expired, but it is worth either re-sending or removing so the member list stays accurate.

What has not been done yet

Stated plainly, so that nothing here is a surprise later.

  • No real users exist yet

    The database is empty apart from the one administrator account. No companies, no staff, no access grants — those arrive with item 08. None of the test data from development was copied across, deliberately.

  • The content is a snapshot, not a live mirror

    Content was copied across on 12 September and does not update itself. Anything edited during continued development will need re-publishing at launch. That is planned for, and is a routine step rather than redone work.

    Technical detail. Nothing synchronises the two environments. Re-running the publish at launch is a scripted step of a few minutes, and it is treated as mandatory rather than conditional — assuming a copy is current, when it is not, has caused a hard-to-diagnose outage on this project before.

  • A full human testing pass is still outstanding

    Automated checks confirm the protections work — private content stays private, and internal files are unreachable. What has not happened is a person clicking through every page on desktop and phone on this specific copy. That pass is scheduled before launch, and the development environment stays available as a reference to compare against.

    Technical detail. What is proven is enforcement: refusals, exclusions and headers, all checked against the live address. What is unproven is presentation on this copy — layout, images, the mobile menu, and browser navigation. The distinction matters: the unverified part is how things look, not whether private content could leak.

  • This is not the launch

    The infrastructure moved early, deliberately, so that you own it from the start and the launch itself becomes a smaller, calmer step. Going live remains a separate, scheduled piece of work.
